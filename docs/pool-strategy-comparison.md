# 池策略对比：workbuddy2api vs dsh-workbuddy2api

本文回答三个「对齐 + 分析」问题：**已对齐了什么**、**两个分析项的结论**、
**是否还需要继续优化**。所有结论都标注了来源（读代码 / 实测），
实测一律通过本机真实账号打真实上游完成。

对齐目标版本：`dsh-workbuddy2api` v0.4.9；参考实现：`D:\Project\workbuddy2api`。
参考实现的权威口径见其 `src/README.md`（错误分类表、选号策略、会话粘性）
与其 `internal/upstream/client.go`、`internal/pool/pick.go`、`internal/pool/cooldown.go`。

## 一、已对齐（本轮新增）

### 1. 模型级冷却（6004）

| | 参考实现 | 本插件（本轮前） | 本插件（现在） |
|---|---|---|---|
| 判定 | 429 body 含 `"code":6004` | 无：429 一律账号级 | `isModelRateLimit()`，容错 `6004` / ` 6004` / `"6004"` |
| 冷却对象 | `modelCooldowns[model]`，**账号不冷却** | 账号级软冷却（**误罚**） | `modelCooldowns[model]` |
| 截止时刻 | `min(上游重置墙钟, now+softRateMax)` | — | 同上 |
| 切模型 | 立刻可用（模型豁免） | **不可用**（账号被冷却） | 立刻可用（`healthyForModel`） |

**为什么必须改**：6004 的语义是「这个**模型**的用量超限」，账号本身健康、
其他模型照常可用。旧行为把整账号停掉 —— 一个能用的凭据被闲置数小时，
而且真正的病因（某个模型被限）被完全掩盖。

### 2. 分层选号（成本分层）

参考实现按**该模型的实测扣费**把候选分三层，硬过滤到最优层：

| 层 | 含义 | 处理 |
|---|---|---|
| 0 | 已实测**免费** | 最强偏好，**硬过滤** |
| 1 | 无观测（含观测过期） | 次优 |
| 2 | 已实测收费 | 层内按单价升序排序 |

**「无观测」排在「已实测收费」之前的理由**（参考实现注释里写得很清楚）：
新号的限免状态只能靠实测发现。若已知收费的号恒压过未知号，
那台免费的号**永远轮不到**，也就**永远学不到**它是免费的。

本插件实现要点：
- 数据来源是上游末帧的 `usage.credit` 与 `total_tokens`（**实测确认存在**，见下）；
- tier 0 是**硬过滤**，tier 1/2 之间是**排序**而非过滤 ——
  两个收费号都保持可用（一个号临时涨价不会饿死另一个），只是便宜的排在短名单前面；
- 观测有 **6 小时 TTL**：覆盖「夜间免费」这类时段性优惠，
  过期观测不会被当成现价（否则白天的选择会被夜里的免费误导）。

### 3. WAF / Retry-After / 重置墙钟

| 触发 | 参考实现 | 本插件（本轮前） | 本插件（现在） |
|---|---|---|---|
| 403 + 无业务信封 | `ErrWafBlock` → 账号软冷却（**不 Disable**） | 落 `client` → **只换号不罚** | `waf_block` → 软冷却 |
| `Retry-After` 头 | 优先采信（秒/毫秒/epoch 三种头） | 忽略 | 采信（三种头都解析，含 sanity 上限） |
| 429 + 「将在 … 重置」 | 冷却到该墙钟，**绝不指数堆加** | 指数退避（**可能等更久**） | 冷却到该墙钟 |

**判定顺序**（自严到宽，每一步都有理由，逐条对齐参考实现）：
`11102 → 402 → session_dead → 429 → 硬额度关键词 → 限流关键词 → 404/5xx → WAF → 其余 4xx`。

两个容易搞错、且都对齐了的点：
- **429 的状态码优先于关键词**：限流 body 高频携带 `quota exceeded`，
  若被硬额度关键词先捕获取，就变成「硬冷却到次日 04:00」，白扔一个号约 12 小时；
- **WAF 判在通用 4xx 之前**：否则 403 落 `client`（只换号不罚），
  于是每个请求都换号、每个都撞墙，永远不自愈。

### 4. 顺带对齐的另外两处

- **session_dead 需要连续 3 次才判死**：单次 12153 多是抖动（连接闪断、
  刷新竞态），一次即禁用会把健康号误杀（参考实现的 P0-1 事故：13 个 disabled 号全是误判）。
  现在的行为：前两次软冷却，第 3 次才硬冷却并提示重新登录；任意成功清零。
- **11102「该后端无此模型」负缓存**：`(账号, 模型)` 维度指数退避
  （6h 起、翻倍、封顶 24h），该模型实测又通了就清除。

## 二、三个分析项的结论

### A. 快过期窗口 —— **发现一个真 bug，已修**

| | 参考实现 | 本插件（本轮前） |
|---|---|---|
| 窗口来源 | `schedule.ExpiringSoonWindow`，**默认建议 7×24h** | `policy.expiringSoonMs = 168h`（声明了！） |
| 实际使用 | 传入 `UserResourceDetailed(a, window)` | **从未读取**：`fetchCredits` 里硬编码 `SOON_MS = 3 天` |

**结论：这是一个「配置项存在但从未生效」的 bug。** 卡片/设置里能改
`expiringSoonMs`，但改了对结果没有任何影响 —— 真正的分桶阈值写死在
`upstream.ts` 的 `SOON_MS = 3 × 24h` 常量里。两者差 4 天：
本该标成「快过期」的 3–7 天内到期积分被漏掉，于是选号时不会优先消耗它们，
积分到期作废。

**已修**：把 `expiringSoonMs` 作为参数传进 `fetchCredits`，
两处调用点（卡片「刷新积分」与网页登录完成后）都传
`pool.currentPolicy().expiringSoonMs` —— 因此**卡片显示的数字与选号用的数字是同一个值**。

### B. 粘性键来源 —— **契约不同，但本插件更稳；已验证**

| | 参考实现 | 本插件 |
|---|---|---|
| 来源 | `metadata.conversation_id` → `metadata.conversationId` → `metadata.user_id` → 顶层 `conversation_id` → `conversationId` | `sha256(第一条 system/developer + 第一条 user)`，前缀 `d-` |
| 稳定键兜底 | `deriveKey`（内容派生） | 同上（内容本身就是键） |
| 重启后 | Redis 镜像（7 天 TTL），否则内存丢失 | 进程内（与参考实现无 Redis 时一致） |

**关键差别与实际影响**：参考实现依赖**客户端显式传会话 id**；
而它在注释里也承认「OpenAI 兼容协议的客户端（dsh / Codex / Cherry Studio）
请求体里既无 conversationId 也无 metadata」→ `sessKey` 恒空 → 粘性**完全失效**。
本插件用内容派生，**恰恰覆盖了这类客户端**，这是更适合 DSH 这个宿主的选择。

**已实测验证一个真实风险并排除**：DSH 的 `dsh-time-context` 插件会往
**每个 step** 追加一条带时间戳的 user 消息
（`Time sampled while preparing turn N, step M: …`）。如果这条消息排在
**第一条** user 消息之前，内容派生的键会**每步都变**，粘性就形同虚设。

实测（`check-sticky-stability.mjs`）：该消息是 **append 到 messages 末尾**的，
而键只取**第一条** system 与第一条 user，因此：

```
step 1 key: d-84ff28005f892f8782744b4a57b2cfab
step 2 key: d-84ff28005f892f8782744b4a57b2cfab   ← 同一会话，键不变
```

**结论：键来源与算法不需要改。** 但这条依赖（"时间戳消息必须排在第一条之后"）
值得记录 —— 若将来 DSH 改成前置注入，粘性会静默失效。

### C. 粘性分配算法 —— **发现一个可优化点，已补**

参考实现是**双段分配**（`session.go` 的 `ResolveForModel` 慢路径）：

1. 优先从**未被任何会话绑定**的可用号里选；
2. 全都绑定了，才回退到全池；
3. 在选中的池子里用 **FNV-1a 哈希取模**（`hashIndex(key, n)`）决定具体账号。

本插件（本轮前）**只有第 3 步的等价物**：绑定失效后重新选号，
直接走加权随机 —— 而权重偏向积分多的号，于是**多个新会话同时开启时，
会一起落到同一个"最富"的账号上**（参考实现注释称之为"惊群集中"）。

**已补上双段分配的语义**（`pick` 里，仅当"有粘性键但绑定失效"时生效）：

```
inUse = 当前被任何会话绑定的账号集合
idle  = 候选里不在 inUse 的
if (idle.length > 0) candidates = idle      // 优先空闲
随后才进入原有的 Top5 + 加权随机
```

三点设计说明：
- **只影响"本来就要重新分配"的会话**：仍持有有效绑定的会话在上面
  fast path 就返回了，压根走不到这里，所以**永远不会被挪动**；
- 保留本插件的**加权随机**而非参考实现的哈希取模：哈希取模在
  请求量小时可能分布不均，加权随机配合"空闲优先"已经能打散，
  且与既有 LRU 兜底、防撞号窗口自然衔接；
- 空闲优先是**偏好不是硬过滤**：一个空闲号都没有时，仍然回退到全候选集
  （与参考实现 `pool2 = uids` 的回退一致）。

实测（新增用例）：把 10000 积分全给账号 a，另两个号只有 1 积分；
三个新会话依次分配 → **三个不同账号**（不补这一步时全都会落在 a 上）。

## 三、还需要继续优化吗？——分三类回答

### 已经足够、不建议再动

| 项 | 理由 |
|---|---|
| 快过期权重系数（`expiringWeight = 8`） | 与参考实现同值；低于积分总量项 ×10 高于闲置项，量级关系正确 |
| 三因子公式主体 | 与参考实现逐项对齐（积分比 ×10、闲置补偿、快过期占比 ×8） |
| 成功率因子 | 双方**都已删除**（终身累计的成功率会让早期出错的号被永久压权），一致 |
| 粘性 TTL（30m 滚动）与 GC（5m） | 与参考实现同值 |
| 防撞号窗口（100ms）与 LRU 兜底（全候选集 + 单调序号） | 已对齐，且本插件同样用 `usedSeq` 单调序号而非墙钟 |

### 想做但**本轮刻意没做**（附理由）

| 项 | 参考实现有 | 为什么不做 |
|---|---|---|
| Redis 粘性镜像 | 有（7 天 TTL） | 本插件是**单进程 DSH 插件**，没有 Redis 依赖；跨重启的粘性对交互式使用价值有限，且会引入一个可选外部依赖。若将来要，可复用刚加好的 `pool-state.ts` 落盘通道 |
| 会话键的 metadata 优先链 | 有 | DSH 的 pi-ai 调用**不传** conversation_id/metadata（已被参考实现自己的注释证实），加上去是死代码 |
| 「连登管家 / 猫猫旅行 / 保活」等排程 | 有 | 属于**任务域**，与本轮池策略无关；成长任务已在 0.4.x 单独实现 |
| 内容拦截降级重试（Degraded 提示词） | 有 | 需要维护一份中性提示词并改写 system，属提示词域；本轮是池策略对齐 |
| 模型级冷却的`ResetAt`台账持久化 | 有（`state.json` 的 `RateLimitedModels`） | **重启即失效更安全**：6004 的重置墙钟是短时窗口（分钟级），跨重启恢复一个可能已过期的墙钟反而会错误地继续避让。参考实现自己也把 `Hits` 特意不落盘 |

### 建议**后续**考虑的（本轮未做，值得单独评估）

1. **成本观测的持久化**：目前观测在内存、6h TTL，重启即清空。
   重新探测的代价是**几毛钱级别的真实扣费**，可以接受；
   但若将来调度频繁重启，可以随 `pool-state.ts` 落盘（参考实现是落盘的）。
2. **模型级冷却的卡片呈现**：本轮已把 `modelCooldowns` 加进池视图
   （卡片会以橙色「模型级限额：glm-5.3 至 …」显示），
   但**没有**在模型选择器里把这些模型标灰 —— 那需要卡片知道"当前 provider
   的某个模型在某账号上被限"，语义上更像"整池都不行"才该提示。
3. **分池（realm）与模型级冷却的交互**：本插件的两区域是**两个独立 pool**
   （比参考实现的 `realm` 字段过滤更彻底），因此不存在跨域误选，
   无需额外处理。
